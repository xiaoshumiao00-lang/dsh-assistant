# 只读文件上限 20MB → 100MB（2026-11-26）

## 一句话
`/api/worktable/file` 的单文件上限改成 100MB（客户端那份同数），并把「`readFile` 整份读进内存再发」改成 `createReadStream` 流式发送；`denyOutside` 目录边界一字未动。

## 原来 20MB 的由来（证据）
- 本仓库第一次出现就在合并提交 `35b3134`（2026-10-26「dsh-assistant v0.1.0」，把 dsh-worktable 与 dsh-pocket 合进来）：`git show 35b3134:src/index.ts` 里已经是 `stat.size > 20 * 1024 * 1024`，同时存在写盘路由的 `content.length > 20 * 1024 * 1024` 和站点路由的 `40 * 1024 * 1024`。
- 那行没有任何注释解释「为什么是 20」，本仓库更早也没有单独引入它的提交；上游 dsh-worktable 的提交历史不在这里 → **未找到确切依据**。
- 合理推断（无直接证据）：当时路由把整份文件读进内存再 `res.end(buffer)`，20MB 是「手机/浏览器都塞得下、Node 不会长时间占几十 MB」的防呆线；站点路由要下发整站资源，所以放到 40MB。

## 是否改流式：改了（附实测）
100MB 文件 + 客户端 5MB/s 慢读，同一台机器实测峰值（`.tmp/mem-probe.mjs`，两种发送方式各跑一次）：

| 发送方式 | 峰值 RSS | 峰值 external | 说明 |
| --- | --- | --- | --- |
| `readFile` + `res.end(buf)` | **324.7MB** | 268.1MB | 整份文件 ≈100MB 常驻，加上待发队列，实测接近 3 倍文件大小 |
| `createReadStream` + `pipe` | **101.8MB** | 45.2MB | 只随页缓存走，基本等于文件大小 |

结论：**必须改**。100MB 时旧写法一次请求就吃掉 300MB+，并发两个手机下载就可能上 600MB（本机 96GB 内存扛得住，但宿主同时还在跑模型/终端，没有理由白占）。
实现要点：`content-length` 用 `stat.size` 且把流的 `end` 钉在 `size-1`（读的过程中文件变大也不会多吐字节）；HEAD 仍然只 stat 不给正文；头发出后流报错只能 `destroy` 连接；客户端断开就销毁流不留 fd。Range 本来就不支持，这次没加也没退步（mp4 inline 拖进度条依旧不行，属原有问题）。
残留风险：手机端 100MB 下载 = 网络传输一份 + 浏览器/WebView 里再存一份，慢是必然；走公网隧道时更慢（隧道与代理本身是 `pipe` 流式转发，不会在中间再整份缓冲）。
