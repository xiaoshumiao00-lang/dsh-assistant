# 手机点图片：不再刷新页面，下载完用看图应用打开——证据、根因、修复（2026-11-27）

> 用户原话：「个人秘书卡片在回复卡片里面，如果是图片的话，点击图片之后很不好，就会让 APK
> 重新刷新、重新进。我希望点击图片之后，就直接在默认的下载器里面下载，下载好之后再用自带的
> 图片查看器查看图片。就是和下载文件的效果一样。」
> 本文只针对这条链路：卡片图片点击 → JS 分支 → WebView DownloadListener → 安卓
> `startDownload()` → DownloadManager → 完成后 ACTION_VIEW 看图。

## 0. 一句话结论

**真因：图片与文件点击原本共用 `openAttachFile → window.open(url,'_blank')`，而 APK 的
WebView `setSupportMultipleWindows(false)` 把它退化成同页导航；服务端对图片回
`content-disposition: inline`（file-disposition.ts 的 INLINE_FILE_EXTENSIONS 含 png/jpg/…），
WebView 就在当前页直接渲染图片，卡片页被整个刷掉（用户看到「APK 重新刷新、重新进」）。
文件不踩坑只是因为 docx 等回 `attachment`，WebView 渲染不了才回调 DownloadListener。**

修法：不新造 JS 桥（App 里本来就没有 `@JavascriptInterface`，事实上的桥就是
DownloadListener）——安卓端图片点击改走**同一条只读路由 + `download=1` 参数**，宿主强制回
`attachment`，WebView 于是把图片交给系统 DownloadManager（带 cookie 的那条原生链路，
f86751b 已修），页面全程不动；下载完成后 `MainActivity` 对图片 `ACTION_VIEW` 拉起系统看图
应用。**改了 Java → 必须重新构建并安装 APK（1.4.6/33 已构建）；只改 JS 的部分刷新页面即可，
但这次必须连 APK 一起换。**

### 1.2 JS→原生「桥」：不存在 `@JavascriptInterface`

- 全 `android/` 目录 grep `JavascriptInterface|addJavascriptInterface`：**0 匹配**。
- 事实上的桥＝WebView `DownloadListener`：`MainActivity.java` **L237-243**
  `w.setDownloadListener(new android.webkit.DownloadListener() { onDownloadStart(...) → startDownload(url, contentDisposition, mimeType) })`。
- 原生下载链路（f86751b 已修，本次复用不动）：
  `startDownload()` **L533-563**（L539-543 `CookieManager.getInstance().getCookie(url)` 塞
  `Cookie`/`Referer` 头、L545-548 照搬 WebView UA、L557 `dm.enqueue`）、
  `fileNameFor()` **L572-590**（RFC 5987 中文名）、`watchDownload()` **L601-625**（完成广播）、
  `reportDownload()` **L627-648**（成功/失败 toast）。

### 1.3 服务端 content-disposition：图片 inline

- `src/file-disposition.ts` **L17-21** `INLINE_FILE_EXTENSIONS` 含
  `png jpg jpeg gif webp bmp svg avif ico …`；**L34-36** `fileDispositionType` 对图片回 `'inline'`；
  L48-54 `contentDispositionValue`、L57-59 `contentDispositionHeaderFor`。
- 路由 `src/index.ts`：`createLocalFileHandler` **L438-444** 写响应头（L442
  `'content-disposition': contentDispositionHeaderFor(abs)`），注册在 **L529-533**
  （`path: '/api/worktable/file'`）。content-type 表 L80-81：png→`image/png` 等。

### 1.4 为什么图片之前会刷页面（因果链）

1. 点图片 → `openAttachFile` → `window.open('/api/worktable/file?path=…', '_blank')`；
2. APK WebView `setSupportMultipleWindows(false)` → 「新窗口」退化成**同页导航**；
3. 服务端回 `200 + content-type: image/png + content-disposition: inline` → WebView 自己就能
   渲染 → **当前页被图片顶替**，秘书卡片页（整个 APK 的 WebView 内容）被刷掉；
4. 文件（docx 等）第 3 步回的是 `attachment` → WebView 渲染不了 → 回调 DownloadListener →
   原生下载，页面不动。这就是「和下载文件的效果一样」的成因差异。

「inline 会打开而非下载」的二选一证据：inline 图片会被 WebView 当页面渲染（§1.4 第 3 步，
真机现象即用户原话）；`download=1` → attachment 后 WebView 渲染不了 → DownloadListener
（路由级单测 §4.2 实测：`download=1` 时回 `attachment; filename*=UTF-8''现场照片.png`，
不带参数仍 `inline`）。故选「**请求参数标明下载意图**」，服务端 inline 口径对桌面保持不变。

**要。** 本次改了 Java（`MainActivity.java` 新增两个方法 + reportDownload 分支），
JS/服务端改动虽然刷新页面就生效，但「下载完成自动拉起看图应用」在旧 APK 里不存在。

宿主侧 JS 强刷一次页面即可。

## 5. 手工验证步骤（真机）

1. 手机装 1.4.6 APK，打开个人助手，进个人秘书会话，强刷页面一次。
2. 让秘书交付一张图片（回复里带 `[[attach:…png|…]]`），卡片出现图片缩略图。
3. **点缩略图**：页面原地不动（不再被图片顶替）；通知栏出现系统下载条目并走到 100%。
4. 下载完成：自动拉起系统看图应用显示这张图；toast「已下载到「下载」并用看图应用打开」。
   （若手机没装看图应用：toast 提示「没找到能看图的应用，点通知栏那条打开」。）
5. 回归对照：点文件条（docx 等）仍是通知 + toast「点通知栏那条可以直接打开」，不自动打开；
   电脑浏览器里点图片仍是新标签页内联看图（桌面行为未动）。
6. 通知栏「下载」里能找到落盘文件（`Download/现场照片.png` 这种中文原名）。
