## 0. 先看现场：当前链路的代码事实

读代码确认的链路（不是猜测，逐条给了文件与行号）：

| 环节 | 位置 | 现状 | 直接后果 |
| --- | --- | --- | --- |

| 段内停顿看门狗 | `lane.ts:1808` 默认 1200ms | 已开始吐块后 1.2s 无下一块就按"中断"收尾 | edge 几乎不流式（首块≈整段），抖动时易误判 |
| 头段等待提示 | `lane.ts:1967` 默认 4000ms | 只提示"合成较慢" | 用户已经干等 4s |
| 本地兜底 | `src/tihu/tts.ts:552`+`:69` `cpuFallbackBlocked()` | CPU 跑 Qwen **直接拒绝**（首包 54485ms【实测】，`tts.ts:40`） | 于是真实链路只剩 edge 一条腿，一断就"念半句就断" |
| 重试 | `lane.ts:1915` 每段最多 2 次 | 只在"还没吐过音频"时重试 | 不解决并发争抢，只放大请求数 |
| 失败告警 | `lane.ts:2000`（跳句红告警）、`lane.ts:2047`（整轮无语音） | 已做到"不静默" | 保留，P0 只补"原因码" |
| 音频块 | `src/tihu/audio.ts:10-16` | 24kHz / pcm16 / 120ms / 2880 采样 / **5760 字节**；`Pcm16Chunker` 压一块给 `final` 打标 | 这套参数很好，**不要动** |
| 下发 | `lane.ts:1782-1796` `flushAudio()` | 合成并发、`tts.audio` 严格按句 index 顺序发 | 顺序对，但被卡住的段会把后面全压住 |
| 协议 | `src/tihu/protocol.ts` | `v:"0"`、字段只增不删、未知 type 忽略；`TtsAudioPayload`(197)、`VoiceInfo`(227) | 协议本身没问题，加字段安全 |
| 页面播放 | `src/tihu/page.ts:1162-1204` | WebAudio 直排时间轴，`startAt = max(currentTime+0.03, pcmNextTime)` | 30ms 提前量太小，抖动就断缝 |
| edge 音色/语速 | `lane.ts:2697` 默认 `zh-CN-YunjianNeural`；`scripts/tihu-edge-tts.py:33` `TIHU_EDGE_RATE` 默认 **+45%** | 语速 1.45 倍 | 快得像赶时间，正是"不像小爱"的主因之一 |
| 本地引擎 | `scripts/tihu-qwen-tts-server.py` + `tts.ts:590` `synthesizeCodec()` | Qwen3-TTS-0.6B 自回归 + 12Hz codec，CPU fp32 | 首包 54.5s（`tts.ts:40`），**必须弃用** |
| 缓存 | 全仓库 | **没有任何音频缓存**（`src/tihu` 里 `cache` 只指会话列表/音色 embedding） | 同一句"好的，我来处理"每次都重合成 |

**一句话诊断**：链路本身（协议、分块、顺序下发、失败告警）是好的，坏在四个数——
分段 32、并发 4×N 路、首块门限 8s 却仍在 12 路争抢、CPU 引擎被 54s 首包废掉；
再叠加"整条回复生成完才开始合成"，用户听到的第一句必然又慢又断。

## 1. 结论与架构总则

### 1.1 四条总则（后面所有设计都从这里推导）

1. **端侧只播放，不合成。**
   ESP32-S3-BOX-3B 是 8MB PSRAM + 240MHz 双核。MeloTTS/Piper 级别的 VITS 权重 208MB/63MB，
   就算 int8 量化到 5–52MB，加上运行时、词表、AEC 与 WiFi 缓冲也放不进 8MB PSRAM，
   240MHz 上 RTF 还会 >1（越念越卡）。端侧只做：收 Opus/PCM → 解 → I2S → 喇叭。
   这正是小爱的真实架构：**云端 ASR + 云端 TTS + 流式回传 + 设备边收边播**，高频短句走预录/缓存。
2. **合成放在宿主（本机）常驻 TTS 网关，零显存。**
   一个独立进程（不是 DSH 主进程内），只绑 `127.0.0.1`，OpenAI 兼容 `/v1/audio/speech`，
   崩溃只影响语音、不拖垮 DSH；`threads` 显式给 6，避开 strata 的 CPU 专家池（15 worker）。
3. **三层解耦：文本前端 / TTS 引擎 / 传输播放。**
   - 文本前端：断句、数字与单位读法、多音字注音（`src/tihu/speech-text.ts` 之后新增一层，**不改屏幕正文**）；
   - TTS 引擎：可替换适配器（MeloTTS / sherpa-onnx / edge / 预录），统一 PCM16 24kHz 输出；
   - 传输播放：固定 120ms 块、按句序、带 seq/ack、页面 80ms 预排、真机 I2S。
4. **单路串行 + 缓存优先 + 失败必告警。**
   本机 CPU 只允许 **1 路**合成（edge 允许 2 路）；同一文本 sha1 命中缓存直接 0ms 首包；
   任何一段失败必须 `event.alert`，绝不静默静音。

### 1.2 目标架构

```
┌────────────┐   ┌──────────────────────────── 宿主（本机，零显存）───────────────────────────┐
│ 唤醒/说话   │   │                                                                          │
│ ESP32-S3   │──►│  tihu lane (src/tihu/lane.ts)                                            │
│ 或模拟页    │   │   assistant/message ──► speech-text ──► speech-normalize ──► splitSegments │
└────────────┘   │                                    （数字/单位/多音字/注音）      │ ≤80字/首段20字 │
      ▲          │                                                               ▼          │
      │          │  ┌──────────── 单路串行队列（每设备 1 条，全局 1 路 CPU）────────────┐   │
      │          │  │ 首段立即合成 ──► 边合边发 120ms 块 ──► 后续段预取（提前量 8s）    │   │
      │          │  └───────────────┬───────────────────────────────────────────────────┘   │
      │          │                  │ ① 缓存命中（sha1，~/.dsh/tihu/cache）→ 0ms 回放          │
      │          │                  │ ② MeloTTS-zh（主，CPU，6 线程）                          │
      │          │                  │ ③ edge-tts（兜底，在线，最多 2 路）                      │
      │          │                  │ ④ 预录音 / 无语音（只留正文 + event.alert）              │
      │          │                  ▼                                                          │
      │          │   tts.audio {seq,total,pcm16,24000,单声道,120ms}  ── 按句 index 顺序下发     │

        binary WS：真机 Opus 24k / 模拟页 PCM16 base64；seq+ack，环形缓冲 300 块可重发
```

## 2. 引擎选型

### 2.1 对比表

"首包"统一按 **20 个汉字**的句子计（≈4.4s 音频），因为 MeloTTS 系是整句合成、非流式，首包≈整句合成时间。

| 引擎 | 形态 / 依赖 | 模型与下载 | 常驻内存【估算】 | CPU 首包(20字) | 流式 | 克隆音色 | 离线 | 维护难度 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **MeloTTS zh_en**（VITS2） | PyTorch 2.x CPU，复用现有 venv | 208MB【标称】+ BERT 子目录 | 1.2–1.8GB（torch 本体占大头） | **0.9–1.5s**（RTF 0.2–0.3【估算】） | 否（整句） | 否（要自己训 VITS） | ✅ | 中（Python + 5 个包 + 词典） | 未采用（原 P0 计划，已被 edge 主用取代） |
| **sherpa-onnx `vits-melo-tts-zh_en`** | 纯 C++/ONNX int8，无 Python | ~110MB（fp32 约 170MB）【估算】 | 250–400MB | 0.6–1.0s | 否（整句） | 否 | ✅ | 低（一个 exe + 4 个文件） | **P1 主引擎替代/无 Python 备用** |
| **sherpa-onnx `matcha-icefall-zh_en`** | ONNX，非自回归 flow | ~120–150MB【估算】 | 250–400MB | 0.5–0.9s | 否（"chunk"只是分块输出） | 否 | ✅ | 低 | 备选（音质略逊 MeloTTS，胜在快） |
| **微软 edge-tts（在线，zh-CN-YunjianNeural）** | 云端 WebSocket + ffmpeg 解 24k PCM | 无本地模型 | 0（每次合成现起 Python 进程） | **2.2–3.3s（8 段实测）** | 准流式（首块≈整段） | 否 | ❌ | 低 | **主引擎（默认）** |
| **sherpa-onnx kokoro（multi-lang v1.1-zh，fp32）** | ONNX，82M 参数，纯 C++/ONNX 运行时 | **随仓库带 400.7MiB**（LFS；model.onnx 310.5MiB） | 300–500MB | **372–1047ms 首块（RTF 0.261–0.515）** | 否（整句，120ms 分块回传） | 否 | ✅ | 低 | **离线兜底（次选）**：试听不如微软自然（实测见 2.2） |
| **MOSS-TTS-Nano（ONNX CPU）** | 18 preset + 零样本克隆 | 727.8MB（`~/.dsh/tihu/models/moss-tts-nano`） | 1.2–1.5GB | **首包 256–514ms**（克隆 861–996ms） | 否 | ✅ | ✅ | 高 | **不用**：WeTextProcessing 装不上（pynini 只有 manylinux wheel），25℃ 读成「周度」、127.0.0.1:3081 读错、日期整句乱；RTF 0.51–0.55@4线程、冷加载 12.6s |
| **piper zh_CN-huayan-medium** | C++/ONNX，16kHz | 63MB；x_low 约 20MB【标称】 | 120–200MB | 0.2–0.4s | 否 | 否 | ✅ | 低 | **只做极速兜底/预录替代**（机械感明显，不像小爱） |
| **Qwen3-TTS-0.6B（PyTorch CPU / GGUF q4）** | 自回归 LLM + 12Hz codec | 1.2GB+ / q4 约 500MB | 3–4GB | **54485ms【实测】** | 名义流式（首包即全部） | ✅ 是 | ✅ | 高 | **可选遗留路径**（只有显式 `TIHU_TTS_ENGINE=qwen` 才启动，见 2.3） |
| **讯飞 / MiniMax 云端**（可选） | HTTP 流式，需联网+计费 | 无本地 | — | 0.3–0.8s（受网络） | ✅ 真流式 | ✅（付费） | ❌ | 低 | P2 可选兜底（隐私与费用要拍板） |

补充事实：
- MeloTTS 中文自然度来自 **jieba 分词 + pypinyin 注音 + chinese-roberta BERT 韵律特征**；
  多音字准确率约 **85%**，可用 `pypinyin.load_phrases_dict` 自定义词典、手动注音或换 **g2pM**
  提到约 **98%**（[腾讯云开发者社区文章](https://cloud.tencent.com.cn/developer/article/2629986)）。
  这正好对上本项目的需求：**我们能改文本前端**，所以 MeloTTS 的短板可以被补掉。
- MeloTTS 纯 CPU 毫秒级合成、208MB 模型的实测报道见
  [这篇实测](http://mp.weixin.qq.com/s?__biz=MzA3MDcwNDY1Mg==&mid=2247484373&idx=1&sn=427572c7d291f22734127e61fc5054ae)。
- sherpa-onnx 的模型清单（含 vits-melo-tts-zh_en / matcha / kokoro）：
  [sherpa-onnx TTS 模型总览](https://mintlify.wiki/XDcobra/react-native-sherpa-onnx/models/tts/overview)；
  纯 C++/OpenVINO 的 MeloTTS 管线：[MeloTTS.cpp-tts](https://github.com/whutbd/MeloTTS.cpp-tts)。
- ESP32-S3-BOX-3B 端侧跑 VITS/Piper 不现实：8MB PSRAM 装不下 20MB+ 的 int8 权重 + 运行时，
  240MHz 上 RTF>1，还会挤掉 WiFi/AEC 的算力。**端侧只解码播放**。

### 2.2 推荐顺序与理由（2026-11-08 第二轮定稿，已落地）

> 下面这套顺序就是当前代码的实际行为：`TIHU_TTS_ENGINE` 默认 **edge（微软 edge-tts 云健）**，
> Kokoro 只在**离线或 edge 不可用**时兜底（次选），qwen 只有显式设置才启用。
> 实测口径：i7-14700KF（strata 常驻吃 8 个 P 核）＋纯 CPU，Kokoro fp32、4 线程、24kHz 单声道。

| 顺位 | 选择 | 理由（实测数字） |
| --- | --- | --- |
| ① 主用 | **微软 edge-tts `zh-CN-YunjianNeural`（在线，语速保持现状）** | 试听效果比 Kokoro 自然；不占本机 CPU/内存。8 段实测首块 **2.2–3.3s**，12 路并发 p99 3.3s；首块门限 **8000ms**（≈2.4×p99，`TIHU_EDGE_FIRST_MS`），首块超时**先重试一次 edge**，仍失败才落兜底。 |
| ② 离线兜底（次选） | **sherpa-onnx Kokoro multi-lang v1.1-zh（fp32，4 线程）** | 实测 **RTF 0.261–0.515、首块 372–1047ms、模型加载 1251ms、段间空隙 0–36ms、CPU 3.9 核**；原生 24000Hz 单声道，正好等于 `audio.ts` 的常量、**不用重采样**；103 音色（中文女 55 / 男 45），自带 `lexicon-zh.txt`（多音字 重庆/银行行长/重载/音乐/系数/宿主机 全对）与 `number-zh.fst / date-zh.fst / phone-zh.fst`；模型随仓库（LFS），clone 即用、不联网。**降级原因：试听效果不如微软音色自然**，所以只做离线/edge 不可用时的兜底，不再默认常驻。 |
| ③ 可选（遗留） | **Qwen3-TTS sidecar** | 只在 `TIHU_TTS_ENGINE=qwen` 时启动（代码保留不删）；CPU 首包 54485ms，克隆音色是它唯一优势 |
| ④ 不建议 | **MOSS-TTS-Nano** | 首包 256–514ms 看着好，但 **WeTextProcessing 装不上**（pynini 只有 manylinux wheel、本机无 conda）→ 25℃ 读成「周度」、IP 地址读错、日期整句乱；冷加载 12.6s、RTF 0.51–0.55。数字读法无法保证，做播报不合格 |
| — | 无语音 | 只留正文 + `event.alert`（绝不静默） |

**Kokoro 不默认自启**：edge 主用时 `backend()` 恒为 `none`，`ensureServer()` 不会 spawn；只有
① 显式「仅离线」/`TIHU_OFFLINE_ONLY=1`/`TIHU_HOST_OFFLINE=1`、② 网络探测失败（连不上
`https://speech.platform.bing.com/`，1.5s 超时）、③ edge 请求失败、④ edge 未安装，这四种
**明确依据**成立时才按需拉起（`ensureKokoroServer()`）；屏上选 `zf_/zm_` 音色也属于手切。
这样用户机器不会白吞 ~300MB 模型加载和 4 个核；切过去的音色设置（sid）保留。

**门限按 edge 主用重取**：edge 首块 **8000ms** 保持不变（不许把 edge 超时拖坏）；Kokoro 兜底首块
`TIHU_LOCAL_FIRST_MS` 默认 **4000ms**（冷加载 1251ms 在 `ensureKokoroServer` 里、不计入请求预算；
之后首块 372–1047ms。兜底没有第二条在线路，宁可多等也不把这一句判死）。
**分段（80 字、首段 20 字）与本地单路串行排队保持不变**（`splitSpeechSegments` + `serializeLocal`）。

**int8 不要用**：同一句话、同一台机器，int8 权重 RTF **1.340**（4 线程）/ **1.712**（2 线程），
fp32 是 **0.477** / 0.873 —— int8 反而慢 2.8–3.5 倍。所以 `TIHU_KOKORO_MODEL` 固定指向
`model.onnx`，驱动脚本还会显式拒绝 int8 文件名。

**线程**：Kokoro 只给 4 个线程（`--num-threads 4`），实测 CPU 占用 3.8–4.0 核；
本地合成在 `tts.ts` 里**串行**（`localPrimary` → lane 的 maxInflight = 1），3 个标签页同时
说话也只能排队，不会把 P 核吃满。

### 2.3 为什么 Qwen3-TTS 必须弃用（不是"暂时不用"）

1. **首包 54485ms【实测】**（`tts.ts:40`，`probe-qwen.mjs`）。而 edge 正常首块 2.2–3.3s。
   一旦用它兜底，等于这一句直接丢掉；代码里已经用 `cpuFallbackBlocked()`（`tts.ts:69`）把它挡掉了。
2. **它是自回归 LLM 式 TTS**（0.6B + 12Hz codec）。CPU 上每多一个字就多一次前向，RTF 随句长线性涨，
   而播报需要"短句快出"——架构上就不匹配。
3. **唯一能救它的是 GPU，而 GPU 没有显存**：strata 常驻已把 16GB 吃满，`--vram-reserve` 下没有余量；
   强行插一个 1.2GB 的 TTS 只会让 strata 换页、解码掉速（MEMORY 里已有 803MiB→453MiB 触发 WDDM 换页的前科）。
4. **收益不成比例**：它唯一优势是零样本克隆音色。若确实要克隆，走 P2 的云端克隆（MiniMax/讯飞）更划算，
   或者用 MeloTTS 自己的多说话人权重再微调（贵，不建议）。

**结论**：`TIHU_TTS_ENGINE` 默认值是 **edge**（微软主用），Kokoro 是**离线兜底（次选）**；
`qwen` 只作为"用户显式指定才启用"的遗留路径保留（`TIHU_TTS_ENGINE=qwen` / `qwen-cuda` / `cpu` / `q4`
都映射到它，代码路径保留不删），文档标注可选。

### 3.4 缓存：sha1 命名，命中 0ms 首包

现状**完全没有音频缓存**（§0 最后一行）。设计如下：

```
key   = sha1( `${engine}|${voice}|${ratePct}|${normalizedText}` )   // 文本用归一化后的（不是屏幕原文）
文件   = ~/.dsh/tihu/cache/<key[0:2]>/<key>.pcm     // 裸 PCM16 LE、24kHz、单声道、无 WAV 头
旁文件 = ~/.dsh/tihu/cache/<key[0:2]>/<key>.json    // {v:1, engine, voice, text, chars, audioMs, bytes, createdAt, hits}
```

要点：
1. **不存 WAV 头**：裸 PCM 正好按 `TTS_CHUNK_BYTES=5760`（`audio.ts:16`）切，回放时直接 `seq=0..n` 下发，
   页面 `playPcm`（`page.ts:1162`）无需改动。
2. **缓存键必须含 engine/voice/rate**：换引擎或换音色后旧缓存不能复用（否则音色串台）。
   语速归一化到整数百分比，`+8%` 与 `+8.0%` 同键。
3. **回放策略**：命中即同步（微任务内）把整段按 120ms 块 `onChunk` 推出去，`firstChunkMs` 记 0–5ms；
   超过 60s 的长音频不缓存（避免一次塞 2.8MB）。
4. **LRU 淘汰**：总容量 `TIHU_TTS_CACHE_MAX_MB=512`，按 `mtime` 淘汰；`TIHU_TTS_CACHE_TTL_DAYS=30`。
   一个 4.4s 段 = 211KB，512MB ≈ 2400 段，足够覆盖"我在""好的""正在处理""已完成"这类高频句。
5. **重复句复用**：同一轮内相同文本（如连续两次"好的"）第二次直接命中；跨轮同样命中。
   预期命中率：固定播报句式 30–50%，首包 p95 从 1500ms 掉到 300ms 以内。
6. **写缓存时机**：整段合成成功且 `audioMs>=300` 才写；失败/半截（stall 收尾）**不写**，避免把断音频固化。
7. **并发写**：先写 `<key>.pcm.tmp` 再 `rename`，避免半文件被读到。

### 3.7 逐轮增量合成（最大的一处体验提升，P1）

现状：`lane.ts:2542` 只在 `assistant/message` 后合成 → 首句必须等整条回复生成完。
`agent/assistant-stream`（`lane.ts:2627`）已经把流接进来了，但只处理 `reasoning-delta`，
注释明写"其它 chunk（text/tool-call）忽略"。

改法：
1. 在 `agent/assistant-stream` 的 `chunk.type === 'text-delta'` 上累积 `pendingText`；
2. 每累积到一个 `HARD_BREAK`（`。！？!?\n`）或长度 ≥80 字，就切出一段**先合成先发**；
3. `assistant/message` 到达时只做"收尾 flush"（补最后半句），不再重新整轮合成；
4. 必须做**去重**：`assistant/message` 的全文会包含已流式发出的句子，按 `charStart` 跳过已发区间。

收益（估算）：首句等待从"整轮生成"（长回复 8–20s）降到"第一个句号"（0.4–1s）。

## 4. 文本前端（决定"像不像人"的一半）

现状 `speech-text.ts:22 toSpeechText()` 只做 markdown 清洗，**屏幕显示与朗读共用一份文本**。
新增一层 `src/tihu/speech-normalize.ts`（实施时新建），顺序固定：

```
原文 → toSpeechText()（现有，去 markdown/emoji/链接）
     → 1 剔除不该念的（代码块/路径/长标识符）
     → 2 数字·单位·符号归一化（cn2an 类）
     → 3 多音字：手动注音标记 → 词典 → 分词 → 拼音校验
     → 4 标点补停顿（输出 pauseMs，不改字符）
     → 5 断句（§3.1）
```

**铁律**：归一化只改"送 TTS 的文本"，屏幕正文永远是 `toSpeechText` 的结果；
且**字符数必须不变或用等长替换**，否则 `charStart/charEnd`（`protocol.ts:185`）与屏帧高亮会全错位。

### 4.1 数字与单位（cn2an 类）归一化清单

| 输入 | 读法 | 规则 |
| --- | --- | --- |
| `1/5` | 五分之一 | `(\d+)/(\d+)` → 分母+"分之"+分子；分子为 1 时用"一"不用"幺" |
| `3:1` | 三比一 | 冒号两侧都是数字且无时间语境 |
| `197.5M` | 一百九十七点五**兆**（数量级）／若后接 `B/字节` 则"兆字节" | `M` 有歧义：数量级读"兆"，容量单位读"兆字节"；**上下文判定失败时默认"兆"** |
| `197.5` | 一百九十七点五 | 小数点读"点"，逐位读 |
| `45%` | 百分之四十五 | `%` → "百分之"+数 |

### 4.3 标点补停顿

MeloTTS 不支持 SSML `<break>`，所以**停顿由音频层补**，不是文本层插符号：

| 标点 | pauseMs | 实现 |
| --- | --- | --- |
| `，` `、` | 180 | 段内不切，仅当该标点落在段尾时补 |
| `；` `：` | 240 | |
| `。` `！` `？` | 320 | 段尾 |
| 段落（`\n\n`） | 500 | |
| 省略号 `……` | 400 | |
| 破折号 `——` | 300 | |

下发方式：`TtsAudioPayload.pauseMs`（§3.6 D1）或直接追加 N 个全零 120ms 块（`data` 为 2880 个 0 采样）。
**推荐后者**：页面 `playPcm` 零改动，`playbackEndAt` 的时长计算也自然对齐（`lane.ts:2009`）。

### 4.4 jieba + pypinyin 自定义多音字词典

MeloTTS 中文前端本身就是 jieba 分词 + pypinyin 注音，所以**最有效的补丁是喂词典**：

```python
# ~/.dsh/tihu/polyphone.py（网关启动时 load）
from pypinyin import load_phrases_dict

load_phrases_dict({
    '重载':   [['zhòng'], ['zài']],
    '行长':   [['háng'],  ['zhǎng']],
    '银行':   [['yín'],   ['háng']],
    '卡住':   [['kǎ'],    ['zhù']],
    '宿主机': [['sù'],    ['zhǔ'], ['jī']],
    '处理':   [['chǔ'],   ['lǐ']],
    '传输':   [['chuán'], ['shū']],
    '系数':   [['xì'],    ['shù']],
    '重庆':   [['chóng'], ['qìng']],
    '西安':   [['xī'],    ['ān']],
    '音乐':   [['yīn'],   ['yuè']],
    '行':     [['xíng']],          # 单字默认；"银行/行长"由词组优先命中
    '了':     [['le']],
    '得':     [['de']],
})
```

注意：
- `load_phrases_dict` 是**词组级覆盖**，优先于单字；单字条目只影响"没有词组命中"的场景，
  所以 `行`/`了`/`得` 这类单字默认值要谨慎（`了` 在"了解"里读 liǎo，需再补 `'了解': [['liǎo'],['jiě']]`）。
- 词典文件用 `~/.dsh/tihu/polyphone.txt`（每行 `词<TAB>pinyin1 pinyin2`）更利于用户手改，
  网关启动时转成 dict；热更新用 `SIGHUP` 或 `POST /v1/reload`。
- **Top 200 词覆盖法**：把用户真实语料里出现过的多音字词导出来排频，前 200 个手工定音，
  实际能消掉 90% 以上的错读，比无脑上 g2pM 便宜得多。

### 4.5 手动注音标记（兜底，用户可写在提示词/回复里）

支持两种写法，**送 TTS 前剥离标记，屏幕显示原文**：

| 语法 | 例 | 解析 |
| --- | --- | --- |
| 单字注音 | `重(chong2)新` | `([\u4e00-\u9fa5])\(([a-z]+[1-5])\)` → 该字定音 |
| 词级注音 | `[重:chong2]新开始` | `\[([\u4e00-\u9fa5]{1,4}):([a-z]+[1-5])\]` → 整词替换为注音后的同形文本 |
| 停顿时长 | `等一下[停顿:300]再说` | 展开为 pauseMs |
| 直读拼音 | `[拼音:ni3 hao3]` | 直接给 pinyin 序列（最后手段） |

实现细节：MeloTTS 的 `text_to_ids` 走 pypinyin，**词级注音最稳**（直接改 pinyin 序列）；
单字注音需要在分词后按字符位置替换，注意 BERT 特征仍吃原文，不影响自然度。

### 4.6 同音字替换兜底（有约束）

引擎怎么调都读错时，用同音字改文本，例如：`重庆`→`崇庆`、`重载`→`众载`、`银行`→`银航`。

**硬约束：只允许等长替换（1 字换 1 字），且不能跨段。**
原因：`charStart/charEnd` 是按**码点下标**算的（`reply.ts` 返回 `start/end`），
一旦长度变化，屏上高亮会整体错位（`lane.ts:2012-2026` 的 `sendReply(... segment.start ...)` 全错）。
等长替换能保证下标不变。不等长的场景一律走注音标记，不改字。

### 4.7 g2pM 值不值得引入

| 维度 | 结论 |
| --- | --- |
| 收益 | 多音字准确率 85% → 约 98%（[来源](https://cloud.tencent.com.cn/developer/article/2629986)）；对"行长/重载/重庆"这类词效果显著 |
| 代价 | 需再拉一个中文 BERT（数百 MB）+ torch 推理；每句增加 **30–80ms**；多一个模型 = 多一个加载失败点；g2pM 训练语料偏新闻，专有名词仍会错 |
| 取舍 | **P2 才做**，且先满足前置条件：① 词典法（4.4）在回归集上仍 <95%；② 首包 p95 还有 300ms 余量；③ 用户接受多下载几百 MB、多 80ms 延迟 |
| 替代 | 词典 + 注音 + 同音字三件套，成本≈0，能覆盖绝大多数真实播报句子 |

## 5. 传输与端侧

### 5.1 音频格式三选一

| 方案 | 带宽 | 端侧成本 | 页面成本 | 建议 |
| --- | --- | --- | --- | --- |
| **PCM16 24kHz 120ms 块**（现状 `audio.ts`） | 48 KB/s 裸；base64 后 **64 KB/s**（每块 5760B → 7680B） | 零解码，直接 I2S | 零改动（`page.ts:1162`） | **模拟页保持**；真机也可先用 |
| **Opus 24kHz 单声道 16kbps**，20ms 帧 | **2 KB/s**（省 24 倍） | libopus 解码，ESP32-S3 约 5% CPU | 需 `AudioDecoder`/WASM | **真机推荐**；端侧缓存也只能用它（30s≈60KB） |
| 现有 `audio.frame`（base64 WAV） | 上行语音用，16k 单声道 | — | — | 不动 |

**决策**：P0 模拟页/桌面继续 PCM16（改动最小、验证最快）；P1 真机切 Opus，
且协议上**按 device capability 协商**（`HelloPayload.capabilities.speaker`，`protocol.ts:101`），
宿主按能力选编码，不搞"一刀切换协议"。

### 5.2 缓冲深度

| 层 | 目标值 | 说明 |
| --- | --- | --- |
| 网关发出 | 首段合成完立刻发，不攒整句 | 首块时延 = 合成首块时延 |
| 页面/设备预排 | **80ms**（`page.ts:1190` 的 30ms → 80ms） | 覆盖 WiFi 抖动 |
| 页面/设备目标 ahead | **600–800ms** | 低于 300ms 开始"饿"，高于 3s 开始"延迟感" |
| 设备环形缓冲 | **300 块**（36s PCM / 6s Opus） | 用于重传，不用于播放 |
| 播放水位 | 起播阈值 2 块（240ms）；低于 1 块插入静音并记 `underrun` | 统计指标 |

### 5.3 乱序、丢包、seq 与 ack

- 现状：`tts.audio` 由宿主按句 index 顺序发（`lane.ts:1782`），跨句不会乱序；**段内**靠 `seq` 单调。
- 新增：
  - 设备每收到 10 块回一次 `tts.ack {index, seq}`；宿主 2s 未收到任何 ack → 认为链路拥塞，
    把 ahead 降到 300ms 并暂停预取（`fill()` 里加 `congested` 判断）。
  - 设备发现 `seq` 跳号 → 发 `tts.resend {index, fromSeq}`；宿主从环形缓冲重发（最多 3 次）。
  - 重传也失败 → 该段补 120ms 静音，继续下一段，并 `event.alert`（不静默）。
- WS 层：`TCP` 本身不丢包，但**页面切后台/手机锁屏**会导致 AudioContext 挂起 + 消息堆积；
  所以 ack 的真正作用是**检测"发了但没播"**，不是补 TCP 的洞。

### 5.4 音量、响度与限流

| 项 | 值 | 说明 |
| --- | --- | --- |
| 目标响度 | **-16 LUFS**（播报），峰值 ≤ **-1.5 dBTP** | edge 与 MeloTTS 输出电平差很多，必须统一 |
| 实现 | 网关按段做 RMS 归一（目标 -20 dBFS 均值）+ 硬限幅 | 比实时 loudnorm 便宜 |
| 淡入淡出 | 每段首尾 **5ms** 线性 | 消"咔哒" |
| 单设备限流 | PCM 64 KB/s（含 base64），Opus 4 KB/s | 3 设备 = 192 KB/s，局域网无压力 |
| 并发上限 | 合成 1 路（本地）/2 路（edge）；**下发不限**（顺序发） | 限的是 CPU，不是带宽 |

### 5.5 设备端（ESP32-S3-BOX-3B）播放要点

| 项 | 要点 |
| --- | --- |
| 采样率 | 24kHz / 16bit / 单声道（与宿主一致，避免重采样） |
| I2S | 主机模式；`MCLK = 256 × fs = 6.144MHz`，`BCLK = 32 × fs = 768kHz`，`LRCK = 24kHz`；ES8311 作 slave |
| DMA | 4 个描述符 × 240 帧（10ms）＝ 40ms 硬缓冲；上层再挂 300ms 环形缓冲 |
| ES8311 | 上电先复位（寄存器 0x00=0x80 → 0x00=0x00），时钟源选 MCLK，DAC 使能，模拟增益初始 -6dB（防削顶） |
| 任务优先级 | I2S 喂数据任务 > WiFi > 屏刷新；喂数据用 `i2s_channel_write` 阻塞式，别用忙等 |
| 播放/采集 | 播放时麦克风仍在采（要 barge-in）；播放 PCM 需重采样到 16k 送 AEC 作参考 |
| 端侧缓存 | 最近 32 条 Opus（≤2MB PSRAM 或 flash 分区），断网可重播 |

### 5.6 AEC 与唤醒词

- **esp-sr 只做命令词识别，不做 TTS**（AFE + WakeNet + MultiNet）。
- 唤醒词「你好，鹈鹕」：WakeNet 自定义词需乐鑫训练/授权；P0 先用内置词（如"你好小智"）
  或按钮触发，把语音链路跑通；P2 再谈定制。
- AEC：esp-sr 的 AFE 需要**16kHz 回采参考**。播放是 24kHz，必须重采样后喂进去；
  扬声器音量 >70% 时残余回声会误唤醒 → 播报期间把唤醒阈值调高或短暂关闭唤醒（代价是丢失 barge-in）。
- 真 barge-in（边说边打断）需要硬件 AEC 收敛良好，BOX-3B 的腔体+喇叭建议实测回声抑制 ≥20dB 再开。

### 5.7 离线模式

| 断点 | 行为 |
| --- | --- |
| 外网断、局域网通 | 本地 Kokoro 兜底照常；edge 自动跳过（`TIHU_OFFLINE_ONLY=1` / `TIHU_HOST_OFFLINE=1` / 探测失败 / edge 请求失败） |
| WiFi 断 | 端侧只播：预录 8 条 + 本地缓存 32 条 + 屏幕提示"离线" |
| 网关崩 | `tts.ts` 看门狗重启；重启失败 → 降级 edge；edge 也失败 → 无语音 + 红告警 |
| 模型文件损坏 | 启动自检 sha256，失败则 `event.alert` 并降级 piper/预录 |

## 6. 延迟预算与稳定性指标

### 6.1 端到端首句延迟预算（从"VAD 判定用户说完"到"听到第一个字"）

| 段 | P0 目标 | 来源 / 依据 | 削减手段 |
| --- | --- | --- | --- |
| ① 设备收音 + VAD 收尾 | 300–500ms | 端侧固定开销 | VAD 尾部 300ms（不要 500ms） |
| ② `audio.frame` 上传（16k WAV，3s≈96KB→base64 128KB） | 50–150ms | 局域网 | 直传二进制（P1） |
| ③ 宿主 ASR | 400–900ms | `lane.ts:96` 超时 45s，**实际值未测**→ 必须 bench | 用流式 ASR；短句优先 |
| ④ LLM 首句（到第一个句号） | 400–900ms | 现状要等**整条** `assistant/message`（`lane.ts:2542`） | §3.7 增量合成 |
| ⑤ 文本前端（清洗+归一+分词+注音） | 15–40ms | jieba 5ms、pypinyin 4ms、规则 <1ms【估算】 | 正则预编译、规则表缓存 |
| ⑥ TTS 首包（MeloTTS，首段 20 字） | 900–1200ms | RTF 0.2–0.3【估算】，需 bench | 首段 20 字、6 线程、模型常驻 |

| **合计（冷启动）** | **≈ 2150–3850ms（p50 目标 2500，p95 4000）** | | |
| **合计（命中缓存）** | **≈ 950–1500ms（p50 目标 1200）** | ①+②+③+④+⑤+0+80 | 缓存是最大杠杆 |
| 挑战目标（P1/P2） | p50 ≤ 1800ms | 流式 ASR + 增量合成 + 云端 TTS（可选） | |

对照现状（估算，非实测）：首句 = 整轮生成（长回复 8–20s）+ 首块 2.2–3.3s【实测】+ 排队/重试
→ **10s 以上，且 12 路并发时 2/3 的段被 0 字节杀掉**。

### 6.2 稳定性指标（验收线）

| 指标 | P0 线 | P1 线 | 现状 |
| --- | --- | --- | --- |

或把 TTS 绑到 E 核（Windows 用 `start /affinity` 或 Process Lasso）。

| `cacheHit` | 是否命中 | 网关响应头 `X-Cache` |
| `gapP95Ms` | 句间静音缝 | 客户端按块时间戳 |
| `underruns` | 饿死次数 | 页面/设备计数器 |
| `successRate` | 并发成功率 | 12/8/4/1 路各 20 次 |

**并发矩阵必须测**：1 / 2 / 4 / 8 / 12 路（对应 1/1/1/2/3 个标签页 × 4 段），
输出"成功率 + 首包 p95"，这是本次整改最核心的证据。

### 7.2 断句正确率抽检

- 语料：从真实会话里取 100 条回复（含数字、路径、中英混、多音字、超长无标点）。
- 抽检 20 条人工判：§8.4 的 8 条标准，全部满足才算过。
- 自动可测部分：段数、最长段、最短段、是否在 `\d` 与单位之间切断、是否把引号切一半。

### 7.3 多音字回归用例（必须逐条听/看拼音）

```
1.  系统正在重载配置，请稍等。
2.  张行长今天去了银行。
```

判定：MeloTTS 输出 + pypinyin 标注双人核对（自己能听懂即可），**12 条全对才算过**；
允许用 §4.5 注音标记修，但修完要回填词典（不能只修一条句子）。

### 7.4 断句验收标准（8 条）

1. 段长 ≤80 字（首段 ≤20）；
2. 无 <12 字的碎段（整条 <12 字除外）；
3. 不在数字与单位之间切（`197.5|MB` ❌）；
4. 不在引号/括号内部切；
5. 不在英文单词/路径中间切；
6. 顿号不单独成段；
7. 段尾尽量是 `。！？`，逗号结尾 ≤20%；
8. 段数与 `tts.text` 的 `total` 一致，`charStart/charEnd` 无重叠无空洞。
