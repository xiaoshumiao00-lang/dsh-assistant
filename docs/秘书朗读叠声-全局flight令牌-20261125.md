# 秘书朗读叠声（同时朗读多个回答）· 根因与修复

> 用户原话（2026-11-25）：「个人秘书会话页面在朗读回答时，有时候会同时朗读多个回答。我希望每次只能够朗读一个回答。当有新朗读时，旧朗读立刻停止。」
>
> 硬保证：任何时刻最多只有一条在出声；新朗读起播的同一瞬间旧的全部停止，**含已排播但还没响的音频块**。
>
> 纪律：本轮**没有** `git commit` / `git push` / 重启宿主 / reload 插件；已 `node build.mjs` 重建 `lib/client.js`（`lib/index.js` 同步重建）。typecheck 本机跑不起来（既有约定），用 `npm run check` + 测试链代替。

---

## 0. 一句话结论

**根因是「唯一性」放错了层**：代码把「同时只有一条在响」寄托在三个**模块内变量**上（`secretarySpeech` 单例、控制器的私有 `player`、每条流水线自己的 `generation`），而真正决定有没有声音的是**共享 `AudioContext` 时间轴上已经 `start(when)` 的 `AudioBufferSourceNode`** —— 这一层没有任何全局权威/登记表。只要出现「正在响的源不属于当前控制器的那个 `player`」的一刻，就没有任何代码会去 stop 它们，于是叠声。**"有时候"**＝这一刻只在播放侧不止一份、且旧的那条还有排在时间轴上的块时才出现；另外同一份代码里还有两条把「一次起播」变成「多次起播」的具体缺陷（§2.4）。修法不是补丁：把唯一性提升为**全局 flight 令牌**，任何一次起播同步吊销上一代登记的全部源（含已排播未响的块），排播每一块前校验令牌，过期即丢。

## 2. 根因

### 2.1 「唯一」只存在于模块内部（三层私有状态）

- `secretary-speech.ts:28-36`：`sharedCtx`（AudioContext 单例）、`:39` 块缓存、`:124` 控制器单例 —— 全是**模块级**变量。
- `secretary-cards.ts:429-506`（旧码 441-467/503）：控制器里 `let player: SpeechPlayer | null`，只有它知道"当前那条播放器"，`start()` 里 `player?.stop()`。
- `secretary-speech-pipeline.ts`（旧码 138）：`let generation = 0`，`swallow()` 只停 `state.playbacks` —— **本条流水线**记过账的块。

三层都在同一个模块实例里。它们共同的盲区是：**不是这套变量创建的、但已经在同一个 AudioContext 上排好时间的源**。

### 2.2 真正出声的是时间轴上的源；Chromium 的 `stop()` 对「已排播还没响」的块确实有效

用真 Chromium（Playwright + `OfflineAudioContext` 离线渲染）实测（探针 `probe-webaudio-stop.mjs`，原始输出）：

```json
{
  "baseline_noStop": { "peakAtWindow": 0.5, "peakAll": 0.5 },
  "stop_noargs": { "peakAtWindow": 0, "peakAll": 0 },
  "stop_zero":   { "peakAtWindow": 0, "peakAll": 0 },
  "stop_now":    { "peakAtWindow": 0, "peakAll": 0 },
  "overlap_both": 1
}
```

（`overlap_both` 是对照组：两个源时间重叠时，区间峰值 = **1**，说明这套离线口子确实能测出「两条同时在响」；`stop_*` 三组都是 0 = 已经排在 0.5s 之后、还没响的源被 stop 后一声不出。）

即：**漏声不是 `stop()` 不灵，而是没有人去 `stop()`**。所以要建立的是「谁有权吊销时间轴上的源」这套权威，而不是再调 stop 的时机。

### 2.3 单一实例内部**不可能**叠声（600 轮随机交错，0 越界）

用真实 `lib/index.js` 的 `createSpeechController` + `createChunkPipeline`，配一个按 Web Audio 语义记账的假播放器（`stop()` 在 `when` 之前 = 该块永不出声；在 `[when, when+dur)` 之间 = 只在调用前有声），随机交错驱动：request 换轮、**同 key 重复 request（绕过去重，模拟重挂载）**、toggle、restart、stop、合成晚回、时钟推进到块播完：

```
单实例全事件随机交错：600 轮，越界 0 轮     （fuzz-all-events.mjs）
单控制器随机交错：    400 轮，越界 0 轮     （fuzz-single-controller.mjs）
```

**推论（这是本次根因的硬证据）**：单实例的时序逻辑本身是干净的 —— 用户听到的叠声必然来自「播放侧存在第二份（或更多）」这一条件，而现有代码对这一条**零防线**（§2.4 两个洞就是它的入口）。

### 2.4 把「一次起播」变成「多次起播」的两个具体缺陷（可直接复现）

1. **同 key + `loading` 重入会第二次 `start()`**（旧码 `secretary-cards.ts:480`）：
   `if (next.key !== before.key || next.status === 'loading') start(key)`。
   状态机对「同 key + loading/playing/paused」是**原样返回同一个 state 对象**，所以 `next.status === 'loading'` 会把「同 key 仍在 loading」也当成要起播 → `start()` 再跑一遍：旧播放器被 `stop()`，新播放器**从第 0 块重排整段文本**。一次朗读被反复起播，任何一次 stop 落空（见 2）就是一路多余的声音。实测旧码：同一 key 连续 3 次 `request` → `start` 了 **3** 次（应 1 次）。
2. **in-flight 合成回来时只校验本条流水线的代数**（旧码 `secretary-speech-pipeline.ts:201`）：
   `if (state.gen !== generation) return` —— 只防住「本流水线自己的 stop/restart」，**防不住另一起播**（另一条流水线/另一个控制器）。实测旧码：另一条流水线起播后，旧流水线的合成回来仍会排播 **2** 块（应 0 块）—— 那 2 块就是叠在别人身上的旧朗读。

### 2.5 与共享 AudioContext 的 `suspend/resume` 关系（已确认不依赖它来静音别的朗读）

`pause()` 仍走 `io.suspend()`（只用于用户手动「暂停当前这条」），但**保证不再依赖 suspend**：新朗读起播时是 `begin()` 直接 `stop()` 掉旧源，`resume()` 把时间轴解冻也不会让旧声音复活 —— 旧的源已经被 `stop()`，与 ctx 状态无关（§2.2 已证 stop 有效）。

## 3. 修法（按真因，不堆补丁）

### 3.1 新文件 `src/client/pocket/orb/secretary-speech-flight.ts`：全局唯一 flight 令牌表

- 语义：`begin()` = 起一代新 flight，**同步**执行上一代登记的全部取消器，返回新令牌；`isCurrent(token)` = 排播准入；`register(cancel, token)` = 把「怎么掐掉这一块」登记进令牌表（令牌已过期就**当场掐掉**并拒绝登记 = 过期即丢）；`cancel(token)` / `cancelAll()` = 吊销。
- **令牌表挂在 `globalThis` 上**（浏览器 = `window`，键名 `__dshSecretarySpeechFlight`，带 `version`）。同一 realm 内不管模块被求值几次，`speechFlightBus()` 返回的都是**同一个对象** —— 这就是「第二份播放侧也能被掐掉」的关键。版本不兼容时先 `cancelAll()` 旧的再装新的，绝不让两套表并存。

### 3.2 流水线接入（`secretary-speech-pipeline.ts`）

| 位置 | 改动 |
| --- | --- |
| `:23` | 引入 `speechFlightBus` / `SpeechFlightBus` |
| `:105-113` | `ChunkPipelineOptions.flight?`（默认取 globalThis 那一份） |
| `:149` | `const flight = options.flight ?? speechFlightBus()` |
| `:156-166` | `RunState` 增 `token` / `unregisters` |
| `:195-201` | `swallow()` 先注销令牌表登记，再 abort 合成、stop 已排播块 |
| `:207` | `alive(state) = gen 最新 && flight.isCurrent(token)` |
| `:226`、`:232` | 等合成前/后各判一次 `alive()`，过期立即 return（**不许把旧朗读的块排上时间轴**） |
| `:233-237` | 每排一块立刻 `flight.register(playback.stop, token)` |
| `:249` | `ended` 回调也走 `alive()`（换代表后旧 finished 不许误报播完） |
| `:271` | `play()` 里 `const token = flight.begin()` —— **起播的同一行里先掐后播** |
| `:285-299` | `stop()`：`generation+1` + `swallow` + `flight.cancel(token)`（双重保底）；`current === null`（从没起播/已停过）时**不做**全局吊销，避免误停别人正在播的朗读 |

### 3.3 控制器去重（`secretary-cards.ts:474-489`）

`if (next !== before) start(key)` —— 用状态对象的**同一性**判断「这次 request 真的换了一条 / 从 error 重来」，同 key + loading 的重入不再第二次 `start()`。

### 3.4 自动朗读去重提升到全局（`secretary-speech.ts:133-161` + `SecretaryReplyCard.tsx:37/456-467`）

`requestAutoReadOnce(scope, key, text)`：去重集合挂在 `globalThis.__dshSecretaryAutoReadKeys`，**带会话 id**（换秘书会话时轮次号会重号，不能把新会话第 3 轮当成已读过的第 3 轮），上限 400 条 FIFO。卡片里原来的 `autoReadKeys`（`:37`）保留为本实例快路径，**唯一权威是全局表** —— 模块再次求值或卡片整棵重挂载都不会把同一轮再请求一遍。

## 6. 生效方式

**用户只需要刷新页面（普通 F5；没变化就 Ctrl+F5 硬刷新）。不需要重启宿主，也不需要 reload 插件。**

依据（本轮实测，不是记经验）：

1. 宿主实际加载的安装副本 `%USERPROFILE%\.dsh\profiles\desktop\node_modules\dsh-assistant` 是 **Junction → `D:\dsh-assistant`**（`LinkType=Junction`），两侧 `lib/client.js` 的 SHA256 完全相同（`55F536DC…C42E21`）—— 宿主读的就是这次重建后的文件，没有第二份副本要同步。

3. 同一插件、同一机制今天已经实测过一次「重建 `lib/client.js` → 刷新页面生效、不用重启宿主」（见 `docs/设置页-CU-面板空白-根因-20261125.md` 一类既有记录与 `MEMORY` 里的固结论断）。

## 7. 汇总（用户要看的两条）

### ① 用户要做什么才能看到修复

1. **刷新个人秘书页面**（F5；不放心就 Ctrl+F5）。
2. 让秘书连续回答两条（或长回复朗读到一半时再问一句）。预期：新回答起播的瞬间旧朗读**一声不留**地停，含刚排在时间轴上还没响的块。
3. 想自检也可以开控制台：`window.__dshSecretarySpeechFlight.current()` 每次起播 +1，同一个对象只有一个（不存在第二份令牌表）；`window.__dshSecretaryAutoReadKeys.size` 每张新卡自动朗读 +1，同一轮不会重复增加。
4. **不需要**重启宿主 / reload 插件；如果刷新后仍能听到叠声，先停下告诉我（那意味着宿主侧缓存了旧 bundle，要重载插件，我需要你同意）。

### ② 单例与去重是怎么被证明的（证据）

**"播放侧只有一份"不是假设，是查过的**：全仓库 `createSpeechController(` 只有 1 处调用（`secretary-speech.ts:124`）；`AudioContext` 播放路径只有 `secretary-speech.ts` 一条（`voice.ts` 是录音、不出声），无 `speechSynthesis`，宿主侧无播放代码；自动朗读入口只有 `SecretaryReplyCard.tsx` 一处；今天现场只有 1 个 DSH 窗口、0 个浏览器标签（前台会话看屏确认）。

**"单实例内不可能叠声"有反证法级证据**：用真实控制器+流水线跑 1000 轮随机交错（含同 key 重入、toggle/restart/stop、合成晚回、时钟推进）→ **0 次越界**。所以叠声只能来自「第二份播放侧」这个条件，而旧代码对它零防线。

**"第二份也能被掐掉"由新测试直接证明**：`test-secretary-speech-flight.mjs` 第 1 条用例造的就是两份播放侧 + 「一块在响、一块已排播未响」的交错，旧码实测两条同时在响（A `[100.03,102.03)` 与 B `[101.03,103.03)`），新码 0 重叠且 A 的未响块也被 stop；第 3 条用例证明同一 realm 两次取令牌表拿到**同一个对象**（`speechFlightBus(fakeRealm) === speechFlightBus(fakeRealm)`）、`begin()` 让旧令牌立刻失效、过期令牌登记会当场掐掉（`calls === ['a','late']`）。

**"去重"的证明**：第 2 条用例——同 key 仍在 loading 时连续 3 次 request，工厂 `start` 次数旧码 3、新码 1；自动朗读去重表本身挂在 `globalThis`（跨模块实例同一份，带会话 id），因此模块再次求值/卡片重挂载都不会把同一轮再读一遍。

**"stop 真的能掐掉还没响的块"有浏览器级证据**：真 Chromium 离线渲染，不 stop 峰值 `0.5000`、`stop()` / `stop(0)` 后 `0.0000`；两个源重叠的对照组峰值 `1.0`（说明测量口径本身能测出叠声）。
