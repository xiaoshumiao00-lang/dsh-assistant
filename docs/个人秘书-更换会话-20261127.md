## 0. 结论

个人秘书的绑定目标从「插件里写死的那条」变成「控制室卡片上一次点击就能换的一条会话」：

- **入口**：控制室「个人秘书」卡片底部操作行多一个「更换会话」按钮（与「会话列表」同一套按钮样式与尺寸，26px 高、整行宽）。
- **面板**：点开弹会话选择浮层（标题 + 相对时间 + 「当前绑定」标记 + 搜索框 + 滚动列表），当前绑定的那条**保留展示但置灰不可再选**。
- **后端**：新增一条宿主路由 `GET/POST /api/assistant/secretary/sessions`：GET 列宿主会话表里所有可绑定的会话；POST 只接受**宿主会话表里认得到的 id**，写盘后**必须回读**，回读不成立就把之前那条恢复回去。
- **切页**：绑定成功后复用既有「进秘书」链路（`openAssistant()`，打开目标以宿主 state 为准），秘书页直接落在新会话上——**不需要刷新页面**。
- **写坏 state 的防护**：id 形状 → 宿主会话表存在性 → 原子写盘 → 回读校验 → 本地缓存最后才更新，一共 5 道，任何一道不过都不改绑定。

## 3. 接口契约

### 3.1 `GET /api/assistant/secretary/sessions?q=<关键词>&limit=<n>`

- 参数：`q` 可选（≤80 字符，匹配标题 / 会话 id / 目录，大小写不敏感）；`limit` 可选（默认 200，上限 600，非法回默认）。
- 数据源：`sessionQuery.listSessions()`（持久化清单）∪ `ctx.sessions.list()`（活会话表），按 id 去重、同一条取较新的 `updatedAt`、带上 `live`。
- 口径：已归档的丢；按 `updatedAt` 倒序；`limit` 截断但当前绑定的那条永远保留。
- 响应 200（真实结构，字段顺序即 JSON 顺序）：

```json
{
  "ok": true,
  "sessionId": "session-83bca3e3-bcd1-49f0-8b3c-2ec9edae14e3",
  "updatedAt": "2026-11-21T13:03:21.075Z",
  "query": "",
  "limit": 200,
  "total": 2,
  "returned": 2,
  "truncated": false,
  "source": "session-query",
  "items": [
    { "sessionId": "session-1111aaaa-2222-3333-4444-555566667777", "title": "Alpha 温度场复核", "updatedAt": 1760000400000, "cwd": "C:\\work\\alpha", "bound": true },
    { "sessionId": "session-2222bbbb-3333-4444-555566667778", "title": "Beta 报告初稿", "updatedAt": 1760000300000, "cwd": "C:\\work\\beta", "live": true }
  ]
}
```

- `source`：`session-query`（两路都有）/ `sessions-list`（只有活会话表）/ `none`（都问不出 → `items: []`，客户端据此降级用本页快照）。
- `total` = 过滤（搜索 + 丢归档）之后的候选条数；`truncated` = 是否被 `limit` 截断（归档过滤不算截断）。
- 缓存头：与既有 assistant 路由同一套 `sendJson()`（`src/assistant-secretary.ts:392`），响应一律 `cache-control: no-store`；客户端请求也带 `cache: 'no-store'`。

### 3.2 `POST /api/assistant/secretary/sessions`　body `{ "sessionId": "<id>" }`

- 校验顺序：JSON body ≤4KB → `sessionId` 形状（`^[A-Za-z0-9._:-]{1,256}$`）→ 与当前绑定相同则 `unchanged: true` 直接回 → 宿主会话表存在性 → 写盘 → **回读校验**。
- 成功 200：

```json
{ "ok": true, "sessionId": "<新 id>", "updatedAt": "2026-11-27T00:40:12.345Z",
  "previous": "<换之前那条>", "verified": true, "readBack": true,
  "dispatchPolicy": "default-computer-use-v2" }
```

- 失败（都不写盘）：
  - `400 {"ok":false,"error":"invalid-session-id"}`
  - `400 {"ok":false,"error":"session-not-in-host-list","sessionId":"<当前真正挂着的那条>"}` ← 主防护
  - `400 {"ok":false,"error":"no-session-source","sessionId":…}` ← 宿主会话表都问不出，宁拒不改
  - `413 {"ok":false,"error":"too-large"}`
  - `500 {"ok":false,"error":"state-write-failed","message":"…","sessionId":…}`
  - `500 {"ok":false,"error":"state-read-back-mismatch","sessionId":"<恢复后>","restored":true|false}`
  - `DELETE` → `405`（重置仍走既有 `DELETE /api/assistant/secretary`）
- 既有 `POST /api/assistant/secretary`（重建链路在用）**一个字没改**，两条职责分开：老路由留给「固定 id 已失效 → 新建一条并把 state 指过去」，新路由留给「用户主动换绑定」。

### 3.3 有关 `denyOutside` 的说明

`denyOutside` 是**文件路径 allowlist** 边界（`src/index.ts:498`，给 `/api/assistant/file|fs|skills|write|mkdir|git` 这些能碰任意路径的路由用）。秘书绑定这两条路由只写 profile 目录下那一个固定文件名（路径在插件内部拼死，不接受任何用户路径），所以边界用不上路径 allowlist，用的是：**id 正则 + 宿主会话表存在性 + 4KB body 上限 + 回读校验**。

## 4. 「选完秘书页要不要刷新」——明确答案

**不需要刷新页面。**

链路：面板选定 → `POST /api/assistant/secretary/sessions`（宿主写盘 + 回读）→ 客户端确认宿主真值 → 写 localStorage 缓存 → `controlRoomStore.setOpen(false)` 关控制室 → `openAssistant()` 按**宿主 state 里的新 id** 调 `api.openSession()` 让主面板切过去（并顺手把只读档 / 关托管 / 置顶 / 改名重新套在这条新会话上）。

代价与边界：

1. **桌面主面板**：一次 `openSession` 切页，无需刷新（等价于点会话列表里的某一条）。
2. **同一浏览器的其它标签页**：它们的 localStorage 缓存会过期，但下次进秘书时会先读宿主真值再对齐（`assistant-entry.ts` 的 `readHostSecretaryId` 会回写缓存），所以它们**下一次进秘书**就是新会话；不需要手动刷新，但已经打开着旧会话页的标签页不会自己跳过去。
3. **手机端**（pocket / WebView）：同样不需要刷新——它下次点悬浮球 / 抽屉「个人秘书」时会先问宿主。**手机上唯一的例外**：如果手机上正开着旧的秘书会话页，它会一直停在那一页，直到你重新进一次秘书。
4. 若宿主没确认（老宿主没这条路由 / 网络失败），面板会把列表标成「宿主没答上，这份列表来自本页会话快照」，绑定走同一个 POST；POST 失败则在面板里就地显示原因，**不切页、不改缓存**。

## 7. 风险与防护

**写坏 state 的五道闸**（这是本次最在意的风险，MEMORY 里有过「固定 id 指向读不回来的会话 → 悬浮球点了没反应」的实测事故）：

1. **id 形状**：`^[A-Za-z0-9._:-]{1,256}$`，服务端与客户端各查一次（客户端先在本地拦，坏形状一个请求都不发）。
2. **宿主会话表存在性**：`collectHostSessionRows` 走持久化清单 + 活会话表两路；认不到 → `400 session-not-in-host-list`，**不写盘**；两路都问不出 → `400 no-session-source`，宁可拒绝也不猜。
3. **原子写**：`.tmp` + `renameSync`，串行 `chain` 防多客户端互相覆盖。
4. **回读校验**：写完立刻 `readFileState(file)` 比对；不成立就 `restoreSecretaryState(previous)` 把之前那条写回去，并回 500（`restored` 字段告诉调用方恢复成没成）。
5. **本地缓存最后写**：客户端只有「POST 成功 + 宿主 GET 回读一致」之后才更新 `dsh.assistant.secretary.sessionId`；任何失败都不动缓存（避免下次进秘书直接点进坏会话）。

**已知边界 / 没做的**：

- 换绑定**不会**顺带迁移已读卡集合、引用卡、滚动摘要（它们都按 sessionId 分键，换到的新会话自然是干净的一份；旧会话的记录原样保留在 `dsh-assistant-secretary-read.json` / `-quote.json` / `-context.json` 里不删）。
- 换绑定**不会**删除或清理旧会话（一个字都不删）。
- 手机端已经打开的旧秘书页不会自己跳转（见 4.3），需要重新进一次秘书。
- 候选列表不含「已归档」会话；宿主 `header.archived` 字段若某版本不提供，则归档会话会跟着出现（面板仍会在绑定前由宿主复核存在性）。
- 老的、没有 `sessionQuery` 的宿主：GET 只能列活会话表，面板可能不全（会标 `source: sessions-list`）；POST 仍可绑定，只是校验范围变小。
