## 标记格式

`[[attach:<绝对路径>|<显示名>]]`，一行一个，放在正文最后。显示名可省（退化取文件名）。
同一轮重复路径去重（反斜杠/正斜杠、大小写归一）。
展示文本、朗读文本（TTS）、复制文本、折叠行兜底文本都剔除这串标记。

## 服务端响应头实例（`/api/worktable/file`）

- docx：`attachment; filename="__.docx"; filename*=UTF-8''%E6%8A%A5%E5%91%8A.docx`（"报告.docx" 那份实测原样输出）
- png：`inline; filename="___1.png"; filename*=UTF-8''...`
- 图片/pdf/svg/文本 → `inline`；docx/xlsx/pptx/zip/无扩展名 → `attachment`；同时给 `content-length`，支持 HEAD。

## 手机点开 docx 的实际行为

实测方式：Playwright + 本机 Chrome（UA = Android 14 Pixel 7、390×844、isMobile/hasTouch、acceptDownloads），
被测 URL 的响应头由**本次提交里生产代码同一个函数**组装（探针脚本 `.tmp/probe-attach-open.mjs`，不入库）：

| 点击对象 | 浏览器实际行为 | 证据 |
| --- | --- | --- |
| docx | 不导航，**触发下载** | `download` 事件 fired；`suggestedFilename = 申报书 v4.docx`（中文名完整保留） |
| png | `inline`，标签页里直接渲染 | 导航到 `/api/worktable/file?path=…`；`img.naturalWidth > 0`；无 download 事件 |
| HEAD 请求 | 200 + content-length + attachment | 卡片文件条上那行大小就靠它（不读 20MB 正文） |

真机链条（Android Chrome）：点卡片 → 下载文件 → 通知栏/下载列表里点「打开」→ **系统「打开方式」选择器**（已设过默认应用的会直接用它）。
iOS Safari：attachment 会进「下载」/分享面板 →「用…打开」。

**结论：满足「打开的时候可以选择打开程序」；不满足「零点击直接用默认程序打开」。**
差在哪：浏览器拿不到系统的默认应用映射，也没有权限替用户发起外部应用 intent；下载之后的系统弹窗不归网页控制。
网页能做的只有 inline/attachment 这一层，剩下的在系统与 App 侧。

可行的下一步（代价从低到高）：

1. 维持现状（用户原话的「可以选择」已经达到）。
2. 卡片上加「分享」按钮：把文件 fetch 成 Blob → `navigator.share({ files })`，安卓直接出系统分享面板（含「用其他应用打开」）。
   前提是 **secure context**（https 或 localhost），现在局域网 http 不满足，要先上 https。
3. 装一个壳 App：注册自定义 scheme 或 Android Intent URI（`intent://…#Intent;…end`），网页点开直接拉起指定应用——个人助手场景偏重。
4. 服务端把 docx/xlsx/pptx 转 PDF 预览（无头 LibreOffice），手机上直接在标签页里「看」，不依赖 Office；要「编辑」仍得下载。

本次严格按需求边界只做了 A–F，没做 2/3/4。
