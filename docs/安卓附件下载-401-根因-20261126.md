# 手机点 Word 附件：通知栏一直「正在下载」——证据、根因、修复（2026-11-26）

> 用户原话：「我点击个人秘书交付的这个 Word 文件，点击之后手机状态栏有一个一直正在下载的文件，
> 一直下载不下来，也打不开、看不到。」
> 本文只针对这条下载链路：卡片 JS → WebView DownloadListener → 安卓 `startDownload()` → DownloadManager。

## 0. 一句话结论

**真因是鉴权丢失（a），不是 URL 改写、也不是服务端内容长度对不上。**
DownloadManager 是系统下载器，**不继承 WebView 的 cookie 罐**；pocket 代理对没有凭证的
`/api/worktable/file` 直接回 `401 {"error":"unauthorized"}`（24 字节、`chunked`、**没有 content-length**），
下载器既拿不到文件也拿不到总字节数，通知栏就停在「正在下载」不动。
最小修法＝安卓 `startDownload()` 用 `CookieManager.getInstance().getCookie(url)` 取 cookie 并
`addRequestHeader("Cookie", cookies)`（外加 RFC 5987 中文文件名解析、失败可见的 toast）。
**改的是 Java → 必须重新构建并安装 APK；本次 JS 一行未动。**

## 2. 先排除 (b) 下载 URL 被改写

- `DownloadManager.enqueue()` 只接受可解析的绝对 `http(s)` URI；URI 不可用会抛异常，
  落进旧代码的 `catch` → 用户会看到 toast「这个文件要到电脑上下载」。
  **用户看到的是「正在下载」通知而不是那句 toast → enqueue 成功了 → URL 是绝对且合法的。**
- `setSupportMultipleWindows(false)` 确实让 `window.open(url,'_blank')` 退化成同页导航，
  但 DownloadListener 拿到的 `url` 参数**已经是 WebView 解析后的绝对地址**（`onDownloadStart(String url, …)`），
  所以「相对路径」这一路不成立。
- 反证：relay 日志里 `/api/worktable/file` 是活的，比如
  `13:47:09 HTTP GET /api/worktable/file?path=…widget-result.json host=<VPS>:7080` + `13:47:09 -> 404`，
  说明同源访问本身通。

## 3. 排除 (c)「content-length 与流不一致」——200 这条路是干净的

`node scripts\test-local-file-route.mjs` 已覆盖：200 + content-length + attachment、字节完整、
100MB 走分块流式、HEAD 只回头。加上实测（见 E3）：`content-length: 1605394` 与落盘字节
`1605394` **一分不差**，响应流没有问题。

所以「大小未知/通知不消失」不是服务端写坏了，而是 **401 那份响应本身就没有 content-length**（见 E1）。

### E6 旧代码：下载请求里没有任何凭证（`git show HEAD:…/MainActivity.java` 原样）

```java
private void startDownload(String url, String contentDisposition, String mimeType) {
    try {
        String name = android.webkit.URLUtil.guessFileName(url, contentDisposition, mimeType);
        DownloadManager.Request req = new DownloadManager.Request(Uri.parse(url));
        req.setNotificationVisibility(DownloadManager.Request.VISIBILITY_VISIBLE_NOTIFY_COMPLETED);
        req.setDestinationInExternalPublicDir(Environment.DIRECTORY_DOWNLOADS, name);
        DownloadManager dm = (DownloadManager) getSystemService(Context.DOWNLOAD_SERVICE);
        if (dm == null) throw new IllegalStateException("no DownloadManager");
        dm.enqueue(req);
        } catch (Throwable t) {
        toast("这个文件要到电脑上下载");
    }
}
```

### E7 文件名：中文名本来就会被一串下划线顶掉

响应头同时给了 `filename="___________2026-2027-1 _____-_______.docx"`（ASCII 兜底）和
`filename*=UTF-8''…`（RFC 5987 中文名）。`URLUtil.guessFileName()` 只认 `filename=`，
于是落到「下载」里的名字是一串下划线——下完也认不出来（用户「看不到」的一半原因）。

### E8 日志侧能证明什么、不能证明什么（如实写）

`~/.dsh/assistant/tihu-tunnel/relay.log` 逐条记「请求 + 状态」：

```
13:47:09 HTTP GET /api/worktable/file?path=D%3A%5C…%5Cwidget-result.json host=<VPS>:7080
13:47:09   -> 404
```

按路径聚合（全日志 279 条非 200）：`404 × 113`、`403 × 20`、`200 × 1`、`204 × 1`，**该路径没有 401 样本**。
但 relay 日志**不记录请求头**，所以「cookie 有没有带上」没法只靠日志判定；
这就是为什么改成做可复现的对照请求（E1 / E2 / E3 / E4）来定位。

## 5. 根因链（三步）

1. 卡片 → 同页导航到 `/api/worktable/file?path=…`（绝对地址，正确）；
2. WebView 命中 `DownloadListener` → `startDownload()` → `DownloadManager.enqueue()`，
   **请求裸奔：没有 `Cookie`、没有 `dsh_pocket_token`、没有 `dsh-auth-*`**；
3. pocket 代理 401（chunked、无 content-length）→ 下载器无文件、无总大小、通知栏永远 0%。
