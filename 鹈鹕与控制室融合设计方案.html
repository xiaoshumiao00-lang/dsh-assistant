一一句话结论与场景对照表

ONE SENTENCE

控制室是唯一的数据源与决策平面；鹈鹕是它的一块 320×240 外接屏加一套语音外设——两端共用同一份会话快照、同一套卡片组件、同一个悬浮球、同一条语音 lane，差别只在密度与可写范围。

办公室里的复杂任务（带附件、带图片、要指定项目目录）全部在控制室布置，那里有大屏、键盘、拖拽和目录选择；离开办公室时，鹈鹕只承担日常监控与简单语音任务——它能看见所有任务，但不布置复杂任务。两端看到的是同一批会话对象，不存在「鹈鹕的会话」和「控制室的会话」两套东西。

二核心设计原则

六条原则按「数据 → 组件 → 球 → 语音 → 分工 → 交接」排列；每一条都给出可检查的落地位置，避免变成口号。

01控制室是唯一数据源

会话状态只有四态：等你 / 在跑 / 排队 / 完成。四态全部由控制室现有派生链算出：sessionIndex.ts 提供按快照身份缓存的派生索引（宿主发布新快照时 invalidateSessionSnapshotIndex() 失效，旧宿主原地改快照也读不到旧索引）；sessionFactCache.ts 按 updatedAt:running:completed 做版本缓存，保证长任务「开跑很久才结束」时活动行不会错位；sessionStatus.ts 用 hasPendingInteraction() 判定「等你」——注意新版 sessionStatus 为每个会话都保留一行，必须看行内的 pendingInteraction 是否为空，不能用 Map.has()，否则空闲会话会被误判成待回答。

鹈鹕屏只消费同一份协议下发的结果（displayTitle、running、updatedAt、cwd 相对标签），把历史上可能存在过的「鹈鹕侧任务列表」整体删掉，不再自建第二套会话体系。

落地：新增任何状态分支只能落在这三个文件里；lane.ts 与固件侧只做展示映射，禁止复制判定逻辑。Phase 1 验收时用全仓搜索证明「鹈鹕侧 0 处独立状态判定」。

02一套卡片组件，三种密度

同一份 layout schema，三种密度：full（桌面 Web 控制室，卡片含预览行与完整按钮组）、compact（手机 WebView 口袋，单列、字号收一档、按钮收进「···」）、micro（320×240 鹈鹕屏，单卡、标题一行、活动一行、进度条、分页行）。三者只是字段裁剪与排版密度不同，不是三份代码——改一处文案、加一个状态徽标，三端同时生效。

这样做的直接收益：鹈鹕固件侧不必再写一遍卡片布局，控制室也不必为小屏维护一条分叉的渲染路径；「等你／在跑／排队／完成」的配色、光环语义、相对时间格式只有一处定义。

落地：ConsoleCardData → layout({ density }) → 三个渲染器。micro 只取 6 个字段，其余字段在序列化前就被裁掉，减少跨端 payload。

03两个悬浮球合并为同一逻辑球

球身显示当前状态计数（等你 n / 在跑 n）与琥珀黄待决策光环：有 pendingInteraction 时呼吸脉冲；进入完成态改为静态绿（不脉冲），点卡片确认后 ack，光环熄灭。这条「完成态静态绿 / 确认即熄灭」的语义原样保留，不因为合并而丢。

球上长按 600ms 或点击切换「办公室 / 外出」视图密度，沿用鹈鹕音量模块既有的长按节奏（600ms 起、100ms 一步），保证手上肌肉记忆一致。桌面 Electron 悬浮球（desktop-ball.ts 的独立透明小窗）与鹈鹕屏球共用 ballConfigStore 里同一份配置——位置、直径、透明度、光环样式、双击行为、当前密度；任一端修改，另一端下一次轮询即生效。

落地：ballConfigStore 只存一份 JSON，两端读写；ack 记录 { sessionId, updatedAt }，updatedAt 前进则 ack 自动失效、黄灯重新亮起（与 factCache 的版本口径一致）。

04语音共用一条 lane

输入侧：本地 whisper.cpp（D:\dsh-assistant\whisper，CUDA 优先、CPU 兜底）同时喂鹈鹕语音输入与控制室的语音输入入口；默认 medium，加载或推理失败自动回退 small。服务只绑 127.0.0.1:3097，POST /transcribe?model=medium|small，后处理为 opencc 繁转简 + 首尾空白清理 + 整段幻觉过滤。lane.ts 的 transcribeDetailed() 先本地、失败再回退宿主 speech。

输出侧：语音播报统一走鹈鹕的播放控制与音量手势——单击静音（真写 0）、双击 85、长按 600ms 起 100ms/步 ×2 点往返、15s 兜底定格、松手存 NVS（"tihu"/"volume"），顶部 132×26 小条 2 秒消失。控制室不再接第二家 TTS、也不再维护独立音量，避免「控制室播报很响、鹈鹕很轻」这种割裂。

落地：两端的语音输入都指向同一个 HTTP 服务；播报音量读同一份 NVS／配置；paceWhenDeep 这类节奏开关只影响排队，不影响音量与模型选择。

05复杂任务分流规则

判据很硬：需要附件、需要图片、需要指定项目目录的任务一律在控制室布置。鹈鹕发起的任务只允许文本与语音输入；一旦上游判定命中附件或目录需求，会话挂起（不 failed、不 cancel），卡片立刻打标「待补：附件」「待补：目录」，并归入控制室视图。鹈鹕屏保留一行只读镜像与「去控制室补齐」提示，补齐后自动回到排队、继续原会话。

这条规则的意义不是限制，而是防错：在 320×240 上选目录、传附件既看不清也点不准，一旦允许就必然产生一批「跑错工作区」的会话——那比拒绝更贵。

落地：分流判定放在宿主侧（getConsoleCards 组装时打 pendingAssets / pendingCwd 标记），固件只渲染标记，不做判断。

06移交 / 收回：双向交接

控制室卡片底部有「移交」：把会话从鹈鹕侧移到控制室继续；「收回」：把会话带回鹈鹕，只留只读镜像行。语义只有一个：切换视图归属（viewOwner: 'console' | 'pelican'）。绝不改会话的 cwd——cwd 决定会话属于哪个工作区，是硬约束，也是整个系统里最不能碰的字段。

移交前后，会话 id、cwd、历史、运行状态全部不变，只是「谁能写」变了。收回不是删除，鹈鹕侧看到的仍是最新快照。

落地：交接动作只写 viewOwner 一个字段；Phase 3 验收用 (sessionId, cwd) 哈希断言交接前后完全一致。

三能力矩阵

「可」= 能发起并能写入；「只读」= 看得见、不产生写入；「不做」= 不提供入口，误触也不落库。

四条不可破坏的既有约束（改代码前先对照）

  1. 新增 getConsoleCards 的输入，必须同时接 notifyConsole 失效源——否则数据变了卡片不动，症状是「要切一次页面才更新」。
  2. 跨端与悬浮球轮询的 single-flight 必须配 8 秒 AbortController 超时；超时只丢弃本轮，不能把上一帧状态清空。
  3. 会话列表浮层用 position: fixed，否则会被卡片的 overflow 裁剪，表现为「列表只露一半」。
  4. 点会话列表项只切换会话，不改项目绑定；cwd 是会话归属的硬约束，任何「顺手改一下」都是事故。

七分阶段实施路线

五个阶段，每个阶段都能独立上线、独立回退。回退统一用「一个开关」实现，不回滚代码。

表 4 · Phase 1–5：内容、验收标准与单开关回退
阶段做什么验收标准（可观测）回退开关
P1状态源合一 鹈鹕改为消费控制室下发的会话快照（console card 协议）；删除鹈鹕侧本地任务列表与自建状态判定；四态统一由 sessionIndex / sessionFactCache / sessionStatus 派生。 同一会话在控制室与鹈鹕屏 3 秒内一致（含「等你 → 完成」翻转）；鹈鹕离线不影响控制室；全仓搜索不到鹈鹕侧第二套状态判定。 consoleCardProtocol=off 鹈鹕退回旧本地列表；快照解析失败降级为「上次快照 + 时间戳」只读。
P2三密度 + 球合并 一套 layout schema 渲染 full / compact / micro；两个悬浮球并为一个逻辑球，共用 ballConfigStore；长按/点击切换密度。 同一 layout JSON 三密度均可渲染；球上计数与光环在两个物理端一致；长按切换 ≤ 200ms 且不重连 lane；改一次 ballConfigStore 两端生效。 densitySwitch=false 球只显示不切换；ballConfigStore 读旧键回落默认配置。
P3待补 + 移交收回 分流标记（待补：附件 / 待补：目录）、挂起态、卡片「移交」与「收回」、鹈鹕只读镜像行与「去控制室补齐」提示。 鹈鹕发起命中附件需求，2 秒内出现「待补：附件」并挂起（不 failed）；移交后控制室可继续、鹈鹕留只读行；收回后控制室回到列表；(sessionId, cwd) 哈希交接前后完全一致。 handoffEnabled=false 隐藏移交/收回，归属固定控制室；maxLowLaneWaitMs=0 关闭低优等待，鹈鹕任务不再插队。
P4语音与播报统一 控制室语音入口接同一台本地 whisper；播报走鹈鹕播放控制与音量手势；medium 默认、small 兜底。 同一段 8 秒参考音频两端转写一致（同为 medium）；medium 加载失败自动 small 且界面有提示；播报音量与 NVS "tihu"/"volume" 一致，单击静音立即为 0。 whisperModel=small 强制兜底；voiceLane=off 关闭控制室语音入口；paceWhenDeep=false 深队列不降速，保持旧节奏。
P5媒体与 OTA（可选，保留在鹈鹕） 本地媒体播放接入音量手势；OTA 保持 10 分钟/轮检查、失败退避 10 分钟、启动后首查 20 秒；不把 OTA 状态塞进卡片主链。 OTA 检查不阻塞录音与播报；媒体播放遇到 ASR 自动暂停；OTA 失败只退避、不刷屏、不影响四态计数。 OTA_CHECK_PERIOD_MS=1800000 回 30 分钟；mediaLocal=false 关闭本地媒体播放。

回退思路统一为「单开关 + 默认值即旧行为」：maxLowLaneWaitMs 归零等于不再为鹈鹕低优任务让路，paceWhenDeep 置 false 等于深队列不降速——一个配置项就能退回上一阶段的观感，不需要回滚提交。P1、P3 涉及数据归属，回退开关必须在前端与宿主两侧同时生效，避免「界面回退了、命令还在写」。

八一页结论

融合之后，用户面对的只有一个概念：控制室。鹈鹕不是第二个产品，而是这个控制室的一块外接屏（320×240、micro 密度、只读镜像）加一套语音外设（一条 whisper lane、一套音量手势与播报）。办公室用它布置复杂任务，外出用它看进度、听播报、说一句话；两边看的是同一批会话，只是密度和可写范围不同。

三条边界决定了这个设计能不能长期活下去：

  • 数据只有一份——四态来自同一条派生链，鹈鹕不建第二套会话体系，删掉重复判定比新增功能更重要。
  • 卡片只有一套——full / compact / micro 是密度，不是三份代码；文案与配色只改一处。
  • 红线只有三条——复杂任务只进控制室；移交收回不改 cwd；新增取数必须接 notifyConsole 与 single-flight + 8 秒超时。

下一步建议：先做 Phase 1 的「状态源合一」（收益最大、风险最低、可单独验收），再并行推进 Phase 2 的球合并——球是用户每天第一眼看到的东西，它一致了，融合感就成立了一半。
